# J005 — Generated-Reel supply, joined against a real local Cutroom service

J005 is the joined vertical-slice proof for [ADR-0023](../decisions/0023-generated-reel-supply.md)
and [issue #94](https://github.com/KnowScroll/knowscroll/issues/94), under #9/#8/#72. It follows
[#89](https://github.com/KnowScroll/knowscroll/issues/89)'s own joined proof
([evidence](evidence/cutroom-local/README.md)) and reuses its process-management fixtures
(`scripts/cutroom-local/**`) and `ops/cutroom-host/host.ts`. It exercises the full path — approved
`GenerationBrief` over a seeded library Scroll → operator job on a standin budget grant →
persisted Cutroom request bytes → dispatch commit → real Cutroom run → events/cursor → result +
record → settlement → verified local-host import → immutable `generated_reel` — against a real,
separate generation worker process (`apps/worker/src/generation/main.ts`, `pnpm dev:generation`)
and `ops/cutroom-host`'s real local Cutroom `api`+`worker` processes running upstream's own
stand-in providers. It does not enable live spend, product publication, eligibility or playback.

## Required evidence

| Boundary | Required observation |
|---|---|
| Happy path | One `cutroom_attempt`; events seq-continuous; result/record persisted; settlement moves the reported cost and releases the remainder; a real, ffprobe-verified MP4 at its content-addressed key; `generated_reel` carries `provider_mode`, `truth_state:'synthesis'`, the generated label and full lineage; the engine's own file untouched |
| Generation worker crash (SIGKILL) between dispatch commit and any recorded outcome | A replacement worker reconciles by the ORIGINAL request id (lookup, then at most the bounded identical-bytes resend), never invents a request id; exactly one Cutroom run for that request id; job still completes and imports |
| Cutroom host restart (SIGTERM both roles, api restarted on the same port) while the run is in flight | The worker resumes following from its persisted cursor with no seq regression or duplication; the run completes and imports |
| Operator cancel while the run is genuinely running | Real contract semantics observed and recorded (cancel is effective only once the engine worker processes it); job ends `cancelled`; nothing imported; reservation released per the terminal result |
| Import refusal (containment failure) | Job left honestly unfinished with the typed reason in `status_detail`, never a fabricated success; no `media_object`; no `generated_reel`; reservation still held; retryable while the engine file still exists |
| Cleanup | Every process the journey spawned has exited; no stray disposable database; the owner-local engine on `127.0.0.1:4390` untouched (pids/start-times unchanged); the pinned Cutroom runtime checkout unchanged before/after |

Receipts retain the exact KnowScroll HEAD, Cutroom revision, `host.ts` sha256, the stand-in script
sha256, ffmpeg version, per-scenario expected vs. observed, and the evidence level label **"real
local service with upstream stand-in providers — not real generation."**

## Run

From the repository root:

```sh
. ./scripts/env.sh
pnpm exec tsx scripts/run-generation-journey.ts
```

`J005_ONLY_SCENARIO=S1|S2|S3|S4|S5|S6` restricts a run to one scenario for fast iteration; the
default (unset) runs all six in order and is the actual accepted journey. Each scenario creates its
own disposable `knowscroll_test_gen_*` PostgreSQL database (migrated fresh from
`packages/db/migrations/0001`–`0013`, seeded with one library `asset` row) and its own Cutroom
instance under `$KS_DEV_ROOT/cutroom/instances/gen-journey-<stamp>-<scenario>/`; none of it touches
the owner database, the owner-local stand-in engine on `:4390`, or the pinned Cutroom checkout's own
files. The generation worker runs as a genuinely separate `node_modules/.bin/tsx
apps/worker/src/generation/main.ts` process with an explicit environment (`DATABASE_URL`,
`KS_MEDIA_ROOT`, `GENERATION_*` tuning only — never a provider credential, which this worker never
holds in the first place).

The compiled `GenerationBrief` used throughout is structurally identical (worldId, narration,
claims, criteria, style) to upstream's own `tests/engine/video.ts` `videoRequest()`, so the pinned
`THREE_RANKS` stand-in script (generated fresh each run via
`scripts/cutroom-local/make-standin-script.ts`'s own generator, reused in-process) answers every
planner/witness/judge call the real, non-model pipeline makes for this exact shape.

A full receipt is written to `$KS_DEV_ROOT/cutroom/logs/generation-journey-<stamp>.json`; a
sanitized snapshot and README (exact revisions, per-scenario expected vs. observed, first failures
and corrections) live at [`evidence/generation-supply/`](evidence/generation-supply/README.md).

## Limits

Every provider Cutroom calls here is upstream's own scripted stand-in (model, image, sensor, video,
narration); ffmpeg/ffprobe are the only genuinely real components besides the two real HTTP/SQLite
processes and this repository's own database/worker code. This journey proves no real
model/image/video/voice generation, no live-provider cost behavior (no live grant is created or
exercised; migration 0013's 200-cent live cap is proven separately in
`tests/generation-contract.test.ts`), no product-facing publication/eligibility/serving/playback
(ADR-0023 section 4/5 keeps every Reel this journey produces at `availability:'imported'` only, and
its `provider_mode:'standin'` is immutable so it can never later be relabelled), and no owner
deployment or acceptance. A local fixture's absence of further progress (S3) is an observation of
this run, not a durable guarantee about every possible interleaving Cutroom's own worker could take.

This journey does not prove ContentDemand waiters, reuse planning, publication gates, feed
inclusion, or continuation (the [target supply flow](../architecture/target/23-CONTENT-DEMAND-AND-INVENTORY.md)'s
later stages, explicitly out of scope for this ADR). Only Reel and Scroll are consumption objects;
nothing this journey imports becomes one.

## Verification status

On 2026-09-20, all six scenarios passed twice in a row (146 assertions on the final run), after two
real first-failures were found and corrected during development — a Cutroom-worker-restart timing
assumption (S3) and a settlement-timing race in the journey's own polling (S4), both detailed in
[the evidence README](evidence/generation-supply/README.md#first-failures-and-corrections). The
owner-local stand-in engine's pids and the pinned Cutroom checkout were confirmed unchanged by S6 on
every run.
