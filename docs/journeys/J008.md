# J008 — Real sign-in: request a link, confirm without consuming, sign in once, sign out

J008 is the joined vertical-slice proof for [ADR-0026](../decisions/0026-magic-link-single-user-identity.md)
and [issue #104](https://github.com/KnowScroll/knowscroll/issues/104), under #2/#4/#12/#72.

- **Desired outcome:** requesting a magic link for an unknown address and for the configured owner
  address are indistinguishable; the confirmation link is delivered only through the development
  sink; `GET /v1/auth/confirm` reports validity without ever consuming the token, safe to call any
  number of times; `POST /v1/auth/session` consumes it exactly once and mints a normal, working
  device session (`origin:"magic_link"`, its account); that session authenticates an ordinary API
  call and can sign itself out; a replay of the consumed token and a separately fabricated expired
  token are both refused with the exact same generic shape.
- **Selected architecture:** ADR-0026, migration 0016 (already on `main`/this branch, unmodified),
  `packages/db/src/sign-in.ts`, `apps/api/src/sign-in-routes.ts`, `apps/api/src/magic-link-sender.ts`.
- **Expected runtime path:** seed a fresh disposable database's bootstrap owner universe (no
  account yet) → start the real API (`apps/api/src/main.ts`) with its own scratch `KS_DEV_ROOT` and
  a freshly chosen, single-run `KS_OWNER_EMAIL` → request a link for an unrelated address and for
  the owner address, both `202`, byte-identical bodies → read the link from the development sink
  file (never logged) → `GET /v1/auth/confirm` twice, `valid:true` both times → `POST
  /v1/auth/session` once, `200` with a working bearer → authenticate an ordinary call → sign out →
  the same session then fails → replay the consumed token, refused → fabricate an already-expired
  token directly (its `expires_at` cannot be aged out after the fact — the schema makes it
  immutable), refused with the identical shape.
- **Observed runtime path:** matched exactly, on the run recorded below; 19/19 checks passed.
- **Evidence:** exact KnowScroll HEAD, Node version, the disposable database name and a full
  pass/fail ledger are in the receipt written to
  `$KS_DEV_ROOT/sign-in/logs/signin-journey-<stamp>.json`; a sanitized snapshot lives at
  [`evidence/sign-in/`](evidence/sign-in/README.md). **Neither the receipt nor this document ever
  contains the address requested or any raw token** — every check is a boolean, a status code or a
  fixed error shape.
- **Divergence and first failing boundary:** three real first-failures were found and fixed while
  building this slice (not journey-runtime instability) — see "First failures and corrections" in
  the evidence README.
- **Remaining decisions / next action:** sign-in UI on either client surface is the named next
  slice (out of scope for #104); a real mail provider remains an open owner decision before any
  non-local use.

## Required evidence

| Boundary | Required observation |
|---|---|
| No enumeration | An unknown address and the owner address both answer `202` with byte-identical bodies |
| Sink is the only delivery | The confirmation link is read from the development sink file, which never contains an `@` (no address is ever written there) |
| GET does not consume | `GET /v1/auth/confirm` reports `valid:true` twice in a row for the same token |
| POST consumes exactly once | `POST /v1/auth/session` succeeds once; the same token replayed afterward is refused |
| Session shape | The minted session's `origin` is `"magic_link"` and it names an account |
| Ordinary authentication | The minted session authenticates `GET /v1/session` exactly like any other session |
| Sign-out | `POST /v1/session/revoke` succeeds; the same session is refused afterward |
| Unified refusal | The replayed token and a separately fabricated expired token produce the exact same `401 {"error":"Unauthorized"}` shape |
| Cleanup | The API process exits; no stray `knowscroll_test_signin_journey_*` database remains; the scratch development-sink directory is removed; the owner database and the owner-local stand-in Cutroom engine on `127.0.0.1:4390` are never touched (this journey never starts, contacts, or knows anything about Cutroom) |

## Run

From the repository root:

```sh
. ./scripts/env.sh
pnpm exec tsx scripts/run-signin-journey.ts
```

The journey creates its own disposable `knowscroll_test_signin_journey_<stamp>` PostgreSQL database
(migrated fresh from `packages/db/migrations/0001`–`0016`), seeds only the bootstrap owner universe
row (no account — the journey's first sign-in creates it), and starts one real, separate process:
the KnowScroll API (`apps/api/src/main.ts`). That process receives an explicit, minimal environment
(`DATABASE_URL`, `KS_DEV_TOKEN`, `PORT`, `NODE_ENV=test`, and — critically — its **own scratch**
`KS_DEV_ROOT` and a freshly generated, single-run `KS_OWNER_EMAIL`) — never this repository's own
`.env`, never this machine's real `KS_DEV_ROOT`, never a provider credential (this slice never holds
one in the first place).

A full receipt is written to `$KS_DEV_ROOT/sign-in/logs/signin-journey-<stamp>.json`; a sanitized
snapshot and README (exact revisions, the full per-check ledger, first failures and corrections)
live at [`evidence/sign-in/`](evidence/sign-in/README.md).

## Limits

This journey proves the backend contract only: there is no sign-in UI on either client surface
(explicitly out of scope for #104, named as the next slice), so "the confirmation surface" here is
the `GET /v1/auth/confirm` JSON response itself, not a rendered page. The development sink is the
**only** delivery mechanism exercised — no real mail provider exists anywhere in this codebase, and
none is contacted. The HTTP round trip here uses the real sign-in routes end-to-end, but against a
disposable database with a journey-chosen `KS_OWNER_EMAIL`, never the owner's actual configured
address or the owner's actual universe. Sub-millisecond timing-side-channel resistance between an
unknown and an owner address is a design property (matching database work either way) documented in
`packages/db/src/sign-in.ts` and `docs/contracts/bootstrap-http.md`; it is not something this
journey (or any automated test in this lane) measures, since a wall-clock timing assertion would be
flaky rather than meaningful. Rate-limit enforcement under concurrency is proved at the unit and
HTTP levels in `tests/signin-token.test.ts`/`tests/signin-http.test.ts`, not repeated here.
