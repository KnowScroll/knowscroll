# J002 — Two private device sessions survive a privacy epoch fence

| Steering question | Answer |
|---|---|
| Desired outcome | Two operator-provisioned device sessions can use the same service without choosing or reading one another's universe. A session can be revoked or expire, and an old privacy epoch cannot admit work or later mutate projections. |
| Selected architecture | Opaque server-digested device sessions → authenticated HTTP transaction and universe lock → epoch-stamped decision and Ledger/job rows (an exposure derives its epoch through its Ledger event) → separate deterministic worker. |
| Required runtime | Disposable PostgreSQL; a real API process; J002 keeps the worker stopped until a pending old-epoch keep job exists, then starts a separate worker process. |
| Passing behavior | Each session receives its own scope and private decision. Owner B cannot use owner A's decision, exposure, or event. Retry preserves one exposure and one keep/job. B's current-epoch keep projects exactly once, becomes visible only in B's Trace, and excludes that asset from B's next feed. Revoked and expired sessions receive generic 401. A current session minted after an epoch advance receives new work, while old references receive 409 and the old pending job is terminal `discarded` without Trace, Accounts or universe revision mutation. |

## Run

```sh
. ./scripts/env.sh
pnpm exec tsx scripts/run-isolated-session-journey.ts
```

The runner creates and force-drops one randomly named loopback PostgreSQL database. It starts the API as a separate process, then runs J002. J002 provisions two identities through `provisionIdentity`, never prints their tokens, and starts the worker only after it has advanced owner A's epoch with an already-pending job. It saves a receipt containing non-secret causal IDs, projection before/after snapshots, terminal job statuses, source hashes, and the successful token-revocation check. The runner uses an allowlisted process environment, blanks values found in local `.env`, and handles `SIGINT`/`SIGTERM` by stopping child processes before dropping the database.

## Evidence boundary

This is a bounded local development journey, not login, enrollment UX, account recovery, production retention, or proof that one physical person owns a device. The direct SQL in the verifier is limited to the disposable lifecycle setup and persisted-state checks that have no public endpoint in this wave. HTTP owns all normal client admission and cross-universe behavior.

No receipt includes a raw bearer token, token digest, provider credential, or provider call. A passing run proves the observed API/worker/database path on that disposable runtime only; it does not prove production deployment, destructive privacy lifecycle policy, provider isolation, or user usefulness.
