# J004 — Reasoning crash and late-usage boundaries

J004 is a synthetic protocol journey for [ADR-0012](../decisions/0012-reasoning-admission-and-reconciliation.md) and [issue #46](https://github.com/KnowScroll/knowscroll/issues/46). It exercises the released [admission and reconciliation primitives](../operations/reasoning-runtime.md) against a disposable loopback PostgreSQL database, separate API and worker processes, and a local HTTP fixture. It does not enable product provider execution.

## Required evidence

| Boundary | Required observation |
|---|---|
| Worker dies before dispatch intent | Zero HTTP requests; unconsumed reservations can close as `not_sent` |
| Worker dies after intent, before HTTP | Committed dispatch and consumed Permit; no replacement invocation; uncertainty stays held |
| Worker dies after HTTP arrival | Fixture observes exactly one original request; recovery preserves unknown liability and remote capacity |
| Authorization acknowledgement is lost | SQL commit is visible but the worker receives no grant; neither original nor replacement sends |
| Lease A expires and B recovers | A distinct recovery worker advances the fence; stale A cannot authorize or advance private state. Automatic execution requeue remains outside this release |
| Cancellation / deadline | Output is withdrawn; local abort supplies no proof of remote cancellation |
| Clear during a pending response | Real API clear erases private reasoning state; original old-epoch usage settles without recreating it |
| Old clear is retried after later activity | Original receipt returns and newer reasoning state/reservations remain unchanged |
| Duplicate / cumulative / conflicting evidence | Exact replay has no extra debit; newer cumulative evidence charges only the difference; conflicts cannot rewrite accepted totals |
| Nullable usage / unknown remote state | Financial liability and remote slots remain independently held until their evidence arrives |
| Shared-cap conflict / locked universe | Failed admission leaves no partial writes; another ready universe progresses |
| Runner interruption | An independent checker distinguishes one signal, a repeated signal and child failure; it requires explicit cleanup acknowledgement plus independent child process-group and disposable database absence |

Receipts must retain actual source revision and hashes, database identity, process IDs and exits, barrier timestamps, original Attempt/request/dispatch IDs, fixture observations and fresh SQL snapshots of private rows, Permits, reservations, retained accounting, receipts, settlements and bucket adjustments. The old-clear retry compares later private rows and all affected balances before and after the retry. Unknown usage remains null. Fixture responses must never be described as provider evidence.

## Run

From the repository root:

```sh
. ./scripts/env.sh
pnpm exec tsx scripts/run-isolated-reasoning-journey.ts --receipt artifacts/j004.json
pnpm exec tsx scripts/verify-reasoning-journey.ts artifacts/j004.json
pnpm exec tsx scripts/verify-reasoning-cleanup.ts
```

The interruption checker runs SIGTERM, SIGINT, repeated SIGTERM, mixed SIGTERM/SIGINT and child-SIGKILL cases after the API, fixture and worker reach a readiness barrier. SIGINT and SIGTERM received while cleanup is already running are idempotent cleanup requests: the runner retains both handlers until its final manifest is durable, then exits nonzero. The checker records only an enumerated failure classification, exit code/signal and a bounded stderr byte count; it never emits child stderr. It checks the OS and PostgreSQL independently of the runner's cleanup report. Host loss and killing the runner itself with SIGKILL are outside that cleanup claim.

The receipt verifier checks required cases, process separation and exits, original identity relationships, committed intent at the HTTP fixture, exact request counts, reservation/balance transitions, private erasure and later-state preservation. The CLI also compares the receipt's source revision and file hashes with the checkout that produced it. A historical receipt remains dated evidence; it is not proof that a later checkout passed.

## Limits

A consumed dispatch is deliberately ambiguous: observing no request at this local fixture does not justify refunding an unknown real provider call. A fixture request count is not proof of exactly-once provider execution or remote cancellation. Lost acknowledgement is an injected fault after actual PostgreSQL commit, separate from the real worker-kill cases.

This journey does not prove production fairness, authorized context compilation, semantic proposal application, native continuation in the product runtime, scheduled retention, deployment capacity or user usefulness. Those gates remain open under [#7](https://github.com/KnowScroll/knowscroll/issues/7) and related epics. Only Reel and Scroll are consumption objects; no synthetic output becomes product content.

## Verification status

On September 16, 2026, all 13 scenarios passed with four fixture HTTP requests. Independent SIGTERM and SIGINT cleanup checks passed. The [evidence and source receipts](evidence/reasoning-faults/README.md) distinguish implementation checks, actual process observations and remaining limits.
