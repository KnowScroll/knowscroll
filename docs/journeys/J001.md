Android build and lint passed locally and in [CI](https://github.com/KnowScroll/knowscroll/actions/runs/35007382446). There are no Android unit-test sources in this bootstrap; mobile behavior is verified by the three real instrumentation runs below.

## Runtime/product proof

Run API and worker separately, then `pnpm verify:journey`. It consumes one unkept editorial asset and preserves history. It fails honestly on library exhaustion. Do not reset personal state to get a green receipt; use an isolated environment when repeating from a new universe.

On an Android emulator/device: open app → enter Scroll → inspect source and reason → Keep → return → observe retained Trace → reopen discovery → verify the kept asset is excluded. Confirm the same IDs in the database receipt. Also stop the API and verify visible retry without fabricated content/success; restore it and recover.

A source-backed paragraph and a working Keep do not prove improved mental models or the finished interaction grammar. Owner feedback and later longitudinal evaluation are separate evidence.

## Wave-one verification

[Reviewed combined evidence](evidence/wave1-integration/README.md) records source revisions, source hashes, real process observations and the remaining limits. The worker's [mobile receipt](evidence/wave1-mobile/process-death.json) is separate from the coordinator's independent run.

For a repeatable backend run that preserves personal history:

```sh
. ./scripts/env.sh
pnpm exec tsx --test scripts/journey-verifier.test.ts
pnpm exec tsx scripts/run-isolated-journey.ts
```

The runner creates disposable actual/decoy databases and a dynamic loopback port, launches real API/worker processes, checks a passing persisted path, then requires a specific rejection against the decoy database. CI runs this backend journey. It does not prove exclusive worker attribution or automatic cleanup after SIGKILL/host loss. `pnpm verify:journey` still checks an already-running configured environment and consumes one unkept asset.

`python3 scripts/android-journey.py` now includes five instrumentation phases, with force-stop and relaunch between the preparation and restoration phases. It uses only the separately installed `.journey` app and a disposable database. Reading-position writes settle after 200 ms or screen disposal; arbitrary immediate kill during a scroll gesture, lost HTTP responses after admission, physical-device low-memory timing and frame budgets remain unproved.
