# J006 — Publication gates and authenticated media serving

J006 is the joined vertical-slice proof for [ADR-0024](../decisions/0024-publication-gates-and-media-serving.md)
and [issue #100](https://github.com/KnowScroll/knowscroll/issues/100), under #9/#12/#72. It follows
[#94/J005](J005.md) (generation supply) and reuses that journey's seeding shape for one stand-in
`generated_reel` rather than running a real Cutroom instance — ADR-0024's own evidence requirements
allow seeding the rows directly, and #94 already proves the real-Cutroom import path.

It exercises, against a disposable database and two real, separate KnowScroll processes:

- **Desired outcome:** KnowScroll's own gates decide a generated Reel's fate; the database refuses
  hand-set eligibility and enforces the stand-in fence; authenticated `GET|HEAD /v1/media/:sha256`
  streams real bytes back correctly, including Range support, without holding a transaction open
  across the send.
- **Selected architecture:** ADR-0024, migration 0014, `apps/worker/src/publication/{gates,evaluate,cli}.ts`,
  `apps/api/src/{media,app}.ts`.
- **Expected runtime path:** seed one legitimate finished-video `generated_reel` (availability
  `imported`) → run the gate-evaluation worker once → every required gate has a recorded verdict;
  `witness_alignment` is `unavailable`; `eligible` is impossible → a direct SQL attempt to hand-set
  `eligible` is independently refused by the database → run the worker again asking for
  `test_eligible` → the database allows it (disposable database, `standin` provider mode) →
  authenticated HTTP GET/Range against the real API process returns byte-identical content with the
  simulated-media marker.
- **Observed runtime path:** matched exactly, on the run recorded below; 16/16 checks passed.
- **Evidence:** exact KnowScroll HEAD, Node and ffmpeg versions, the disposable database name, the
  generated Reel id, its media sha256/size, and a full pass/fail ledger are in the receipt written to
  `$KS_DEV_ROOT/publication/logs/publication-journey-<stamp>.json`; a sanitized snapshot lives at
  [`evidence/publication/`](evidence/publication/README.md).
- **Divergence and first failing boundary:** two real first-failures were found and fixed during
  development of this slice (not of the journey itself) — see "First failures and corrections" in
  the evidence README.
- **Remaining decisions / next action:** none for this slice; a real Visual Witness implementation
  is the next named dependency before any Reel can reach genuine `eligible` in a real universe.

## Required evidence

| Boundary | Required observation |
|---|---|
| Gate evaluation | Every one of the seven ADR-0024 §2 gates gets a recorded verdict for one stand-in Reel; `witness_alignment` is `unavailable` with a reason naming the missing model |
| Eligibility is structurally blocked | The gate worker's own `auto` decision leaves availability `imported`; a direct SQL `UPDATE ... SET availability='eligible'` on the same row is independently refused by the database |
| Stand-in fence | The same Reel reaches `test_eligible` once explicitly asked, because this run is inside a disposable `knowscroll_test_*` database with a `standin` provider mode |
| Media serving | Authenticated `GET /v1/media/:sha256` against the real API process returns the whole file byte-identical to what was stored; two `Range` requests together reassemble byte-identically; the response carries the simulated-media marker |
| Cleanup | The API process exits; no stray `knowscroll_test_pub_journey_*` database remains; the scratch media directory is removed; the owner database and the owner-local stand-in Cutroom engine on `127.0.0.1:4390` are never touched (this journey never starts, contacts, or dispatches to Cutroom at all) |

## Run

From the repository root:

```sh
. ./scripts/env.sh
pnpm exec tsx scripts/run-publication-journey.ts
```

The journey creates its own disposable `knowscroll_test_pub_journey_<stamp>` PostgreSQL database
(migrated fresh from `packages/db/migrations/0001`–`0014`), seeds the bootstrap owner universe row
(what `pnpm db:seed` would otherwise do) and one fully legitimate finished-video `generated_reel`
row — going through migration 0013's own admission and lineage guards, not around them — with a
real, local-ffmpeg-made MP4 at its content-addressed key. It starts the real KnowScroll API
(`apps/api/src/main.ts`) as a genuinely separate `tsx` process bound to an explicit local port, and
runs the publication-gate worker (`apps/worker/src/publication/cli.ts`) — a one-shot process, since
this slice defines no gate job queue to poll — as a second, separate process, once with the default
`auto` decision and once with `--decide test_eligible`. Every child process receives an explicit,
minimal environment (`DATABASE_URL`, `KS_MEDIA_ROOT`, and for the API `KS_DEV_TOKEN`/`PORT`) —
never this repository's own `.env`, never a provider credential (this slice never holds one in the
first place).

A full receipt is written to `$KS_DEV_ROOT/publication/logs/publication-journey-<stamp>.json`; a
sanitized snapshot and README (exact revisions, the full per-check ledger, first failures and
corrections) live at [`evidence/publication/`](evidence/publication/README.md).

## Limits

The `generated_reel` this journey evaluates is seeded directly with a stand-in provider mode, not
produced by a real (even stand-in) Cutroom run — #94/J005 already proves that supply path; this
journey's scope is publication gates and serving, not re-proving import. `witness_alignment` is
verified `unavailable` by construction (no Visual Witness model exists anywhere in this codebase);
this journey cannot and does not prove what a real witness implementation would decide. The HTTP
round trip here uses the API's own bootstrap development identity (`KS_DEV_TOKEN`), the same
mechanism [bootstrap-http.md](../contracts/bootstrap-http.md) documents; it is not a claim about
production authentication. No owner deployment, owner acceptance, or real generation is proved or
claimed anywhere in this journey.

## Verification status

On 2026-09-20, the journey passed with 16/16 checks against KnowScroll HEAD `472c6b5c4373…` (the
contract-only commit this slice was built from; see the PR that carries this evidence for the exact
delivered revision) and re-passed after the fixes below, detailed in
[the evidence README](evidence/publication/README.md#first-failures-and-corrections):
`apps/api/src/media.ts`'s async handler had to `return reply.send(...)` rather than call it as a
bare statement (an `undefined` return value from an async Fastify handler otherwise races Fastify's
own completion path and truncates the response to `Content-Length: 0`, confirmed directly against
this project's installed fastify/light-my-request versions), and the media-serving authorization
query had to prefer an `eligible` reference over a `test_eligible` one for the same content-addressed
bytes, so real content already reachable through one Reel is never mislabelled simulated because
another Reel also names the identical bytes `test_eligible`.
