## D-015 · 2026-10-19 · @orpc/nest 1.15.7 on Nest 12.1.3 accepted; no OpenAPI-first fallback (S1.2 #225)

Status: accepted (coordinator, 2026-10-19).

The compatibility spike passed in CI through the deployed release trees: contract-first routes with `@Implement`/`implement()` (GET and JSON POST), request-derived callers through Nest's `@Req()` inside the handler closure, input validation, `customErrorResponseBodyEncoder` plus a `sendResponseInterceptors` entry that answers every error as `application/problem+json` (RFC 9457) with stable codes, a Nest exception filter and an Express error middleware for failures outside oRPC (unknown routes, body parser 413/400, non-JSON 415), the typed `@orpc/openapi-client` link from `@knowscroll/contracts`, and OpenAPI generation (`@orpc/openapi` + `@orpc/zod/zod4`). oRPC errors are not the public error format: oRPC's own 4xx codes map to their problem codes (any other 4xx stays a client error), and lock waits, statement timeouts, deadlocks and serialisation failures anywhere in the cause chain answer a retryable 503 with `Retry-After` (logged once as `http.retryable_failure` with their code, since a timeout or deadlock is usually a real fault) instead of a 500. oRPC 2.x (beta, tested upstream on Nest ^12.1.3) is not adopted; revisit when it is stable. OpenAPI-first remains the fallback only if a later oRPC release breaks this test.

## D-016 · 2026-10-19 · Command receipts are an infrastructure facility with their own schema (S1.2 #225)

Status: accepted (coordinator, 2026-10-19), amended after the independent review and re-review of #253.

Blueprint §5 lists "command receipts" under Experience, but every module's commands need them (social, scenarios, privacy), and modules write only their own data. Receipts therefore live in `packages/backend/src/infrastructure/receipts` with the infrastructure-owned schema `receipts`, erased per universe through the erasure registry:

- `personal_commands` keyed `(universe_id, command_id)`, read and written only inside the locked personal scope; the request hash covers the operation and the canonical validated request (keys in code-point order; non-plain data refused) including the revisions it relied on.
- A replay returns the stored outcome only when the receipt's privacy epoch equals the caller's and its `outcome_version` is the one the caller reads. A receipt from before a privacy reset is never replayed; the caller is already at the current epoch, so it answers `COMMAND_KEY_REUSED` (mint a new ID) rather than a reload-and-retry problem that would loop. Outcome versions: a release that writes version N also reads N-1; a receipt written by a newer release (rolling deploy) answers a retryable 503 and is never re-applied; one in a retired older shape answers `COMMAND_KEY_REUSED`.
- `shared_commands` keyed by scope kind and ID, actor, operation and command ID, usable only through a `SharedScopeTx`, which `enterSharedRoot` hands out at most once per personal scope after the personal root is locked (blueprint §19 lock order).
- **Refusals.** Retryable refusals (lock busy, stale epoch, missing or stale asset) write no receipt and are evaluated again on retry. A future command with a *terminal* refusal (for example, sending to a room the person has left) must either store the refusal as its outcome or require the client to mint a new command ID; each such command states which.

## D-017 · 2026-10-19 · Diagnostics carry no free text (S1.2 #225)

Status: accepted (coordinator, 2026-10-19), amended after the independent review and re-review of #253.

`logEvent` fields are IDs, codes, route templates, counts, durations, configuration problems as `VARIABLE: kind_code`, and sanitised errors (class, code, shortened frames; never messages). Framework messages are reduced to recognised lifecycle codes; pg-boss warnings to their kind; plain-object errors keep only their code. The journal projection withholds personal-linkable IDs (blueprint §26 "Logging retention and erasure must agree"). Secret-shaped values are refused even in identifier-shaped fields (the canary test found a token that passed an ID pattern). The same rule covers job state: a failed job's stored output (`pgboss.job.output`, kept for days, dead letters for two weeks) is a code-only record (`{failure, errorClass, code}`), never the error's message, stack or driver detail; a payload that does not match its queue is dead-lettered at once. Consequence: some debugging detail (exception messages) is unavailable in the journal; rich, personal detail belongs in erasable, access-controlled decision records when they arrive.

## D-022 · 2026-10-19 · Identity: first-party magic links and sessions, not better-auth (S1.3 #226)

Status: accepted (coordinator, 2026-10-20; proposed by the S1.3 worker 2026-10-19, revised after the independent review and re-review of PR #257, merged as `d467f664`, applied and verified on dev 2026-10-20). Applies D-007's fallback clause.

D-007 asked S1.3 to prove better-auth first. The spike ran better-auth **1.7.10** (MIT; magic-link and bearer plugins, Kysely adapter with `schemaName: 'identity'` and snake_case field maps, `generateId` → UUIDs) on Nest 12.1.3 / Express 5.2.1 against a throwaway PostgreSQL 16 (hands-on, real database; script and output in `/Volumes/Mrigesh SSD/knowscroll-dev/v2/evidence/s13/spike-better-auth/`, and in branch history at `13f738f6`). What worked: mounting under `/auth/*` before Nest's JSON parser (other routes kept their body parsing), storage in the `identity` schema, hashed single-use tokens (`storeToken: 'hashed'`), cookie and bearer session lookup, an origin check on its own routes. What it cannot satisfy without being taken apart:

1. **A GET signs in.** The link points at `GET /magic-link/verify`; a request with no cookie and no origin — what a mail scanner or prefetcher sends — answered 302 with a session cookie and created a session. The rule is "consumed by POST; a prefetched GET cannot sign in". Keeping better-auth would mean disabling its verify route and calling its server API from a POST of our own.
2. **No account and universe root in one transaction.** `databaseHooks.user.create.after` runs after the user insert (queued after its transaction by design); a failure there left an account without a universe and answered 500. The rule is one transaction with a receipt.
3. **Its error and log formats are not ours.** Errors are `application/json {message, code}`, not RFC 9457 problem details (D-015); it logs free-text messages and stacks (D-017) unless its logger is replaced.
4. **Operator sign-in would couple to its internals** (its verification identifier and value format), and it needs a signing secret per world that we would have to provision.

What remained after the necessary workarounds was a session table and token hashing behind a framework that owns its tables, routes and error shapes. The first-party implementation (`packages/backend/src/modules/identity`, README there) has exactly D-007's properties:

- Links: 32 random bytes (`ksl_…`), only the SHA-256 stored, at most 15 minutes (database check), single use, consumed only by `POST /auth/redeem`. The token rides in the URL fragment; the redeem page first asks `POST /auth/peek` whose account the link opens (the full address for a web link) and redeems only after the person taps "Continue as <address>" (login forgery by link shows itself). Addresses: a strict RFC 5321 subset (printable ASCII, dot-atom local part, LDH domain; anything else `422`). Budgets: 10 requests per client (an IPv6 client is its /64; an in-memory flood brake, not a source of truth) before anything else; then, durably and counting only links actually issued, 3 per address, 60 per recipient domain and 300 per world per 15 minutes (domain and world each under an advisory lock), each answering `429` with `Retry-After`, a filled domain or world budget logged once per window (`identity.sign_in_budget_full`). `202` for every acceptable address and no account created before redemption (no address oracle); one AgentMail send per link, not awaited, never retried. Expired links and long-ended sessions are removed by a scheduled pg-boss job (`identity.sweep-sign-in-records`, every 15 minutes), never in a request.
- Native links are bound to the device (PKCE-style, RFC 7636 S256): the app keeps a verifier in its secure store and asks for the link with its challenge; only the verifier redeems it (and peeks at it). A link asked for without a challenge is redeemed by the web only. This is the device binding §19 asks for; OAuth itself stays out of scope. **Off on every world** (`KS_NATIVE_SIGN_IN_BINDING`) until the native app ships, because as built anyone could bind a person's links to their own challenge and lock the address out of its budget; before enabling it, count the address budget per binding or let the web redeem a bound link with a code from the mail body (re-review N1).
- Redemption: one transaction — address advisory lock → link row lock → find or create account + address + universe root (epoch 1) → `WithResolvedPersonalScope` locks and rechecks the root → receipt `(universe, commandId)` → session. Every refusal rolls the whole transaction back, so a refused redemption consumes nothing. Retrying the same command replays only while the session that redemption issued is still live, and replaces it; concurrent retries and two links for one address never create a second root.
- Sessions: 32 random bytes (`kss_…`), hash stored, 30 days, revocable; web gets an HttpOnly, SameSite=Lax, `__Host-` Secure cookie and cookie-authenticated mutations and socket handshakes must carry the world's `Origin`; native gets a bearer token once for its secure store; a web token is never accepted as a bearer token or vice versa. Authority (account, universe, current epoch) is re-read on every request; revoked or expired sessions are 401.
- The scope claim (one guard in front of every `/v1` route; opt-outs only via the reviewed `UNSCOPED_V1_ROUTES`): every account request carries `X-KS-Scope: <accountId>:<privacyEpoch>` and every socket handshake the same in `auth.scope`; the API serves it only when it names the presented session's account and current epoch (`409 SCOPE_MISMATCH` otherwise, nothing read or written). The client's AccountScope owns its own credential and ends before a switching redemption is sent; on `SCOPE_MISMATCH` it rereads the session. So an account switch in another tab, or a privacy reset whose revocation notice was lost, never serves one scope another's answers.
- Operator sign-in for disposable accounts (`dist/operator.js issue-sign-in`): only in the allow-listed worlds dev, stage, ci and local (refused elsewhere, live included whatever it is called), only with `KS_ALLOW_OPERATOR_SIGN_IN=1`, and only for addresses matching the world's `KS_OPERATOR_SIGN_IN_PATTERN` (dev and stage: `*@test.knowscroll.space`), checked at API startup, at command startup, at run time, when the link is issued and again when it is redeemed. An account whose address proved itself by mail is never opened by an operator link. Each issue writes a durable audit row (`ops.operator_sign_ins`: world, time, `cli:<operator>`, account) that survives "clear history" and becomes a tombstone on account deletion.

## D-034 · 2026-10-24 · Composer buffers and Jev (#234)

The blueprint (§9) leaves these open; this is what the code does.

- **When a buffer is prepared:** when an offer is activated, in the activation transaction, not when the navigation that produced the offer commits. Only then is the encounter really the person's current one and in the recent-repetition input, so the worker ranks what the person will actually move on from. The job is IDs only (`composer.prepare-buffer`).
- **Key and coalescing:** one buffer per person and mode (`vertical`), bound to the session, its intent revision and the source offer and exposure. The job carries the revision; a job whose session moved on does nothing, so a newer activation supersedes older jobs. Preparing replaces the previous buffer and deletes its decision.
- **What is stored:** a normal Composer decision (bound to revision + 1, the revision the serving navigation commits) and a pointer row `composer.buffers` with up to three selected offers and their catalogue watermarks. Serving deletes the row in the committing transaction; a buffer serves at most once.
- **Lifetimes:** a buffer is served for 10 minutes. Stored Jev assessments are valid for 30 minutes and live in the buffer row. After the buffer's life the HTTP path ranks deterministically, using the assessments while they are valid.
- **Serving checks:** transaction 2 rechecks each selected offer exactly as for a fresh ranking (admission at the exact revision, catalogue watermark, Hide, link). Drift deletes the buffer and its decision and allows the existing single rerank.
- **Jev:** role `composer.jev`, version `jev.1`. Criteria: relevance, appropriateness, redundancy, each in [0,1]. `SemanticFit = 0.4 relevance + 0.4 appropriateness + 0.2 (1 - redundancy)`, combined by code. Shortlist: the 20 best eligible candidates by the deterministic baseline. One call per key (no repair); the harness run ID is the queue job ID, so a redelivery cannot pay twice. Failure, refusal or an unusable answer is the absence of an assessment, never a negative judgement. Switch `KS_JEV_ENABLED`, default 0, set to 1 on dev. Model: the harness's configured model; `MiniMax-M3.1-Flash` once #232 lands its adaptive-thinking handling. Limit: the generic personal harness runs only while recording is at its initial generation, so a person who used Pause has no Jev until the recording-aware harness accepts a Composer purpose.

## D-037 · 2026-10-24 · Quartermaster Create, bounded takes and free-text matching (#239, #232)

Scroll production now runs as worker jobs, and a person's request for a topic with no admitted content ends in a produced Scroll. The blueprint (§11) names Create without numbers; these are the choices.

- **Create produces a library recipe, nothing else.** The catalogue is derived from the library plan, and a library test proves every facet has at least one recipe, so a valid catalogue brief always has a recipe. Code builds nothing from catalogue meanings and does no research lookup of its own: the recipe's brief and allowlisted pages are used as they are. A brief with no producible recipe left (all published, or none can be taken again) closes as `could_not_prepare`.
- **Which recipe.** For a brief, the candidates are the recipes that teach its facet, then those that cover it as a supporting facet (every recipe of the planet for a brief without a facet). Prefer one already running (the request joins that work), then one not started, then a rejected one that may be taken again. Published and stopped recipes are never chosen.
- **Only Scrolls, only catalogue meanings.** A Reel, or a variant of an existing explanation, has no production path and closes at once as `budget_unavailable`. A contextual free-text ask closes as `unsupported_request`.
- **One transaction.** Create commits the shared group (`supply.work.production_recipe`), the production job and the request together. A global advisory lock (last in the lock order) serialises Create decisions so the day's count and the group agree. A group whose production ended is closed instead of joined.
- **Daily caps, one per origin.** `KS_SUPPLY_CREATE_DAILY_CAP` productions per UTC day for people's asks, and `KS_SUPPLY_PLANNER_CREATE_DAILY_CAP` (default 5; dev: 5) for the Planner's demand, each counted from `supply.work` rows with a recipe by who commissioned them (`commissioned_by`). The Planner's effective cap is never above the people's cap, and it cannot use what an explicit ask needs. People's default is 20 in `local`, 0 elsewhere (dev: 10); 0 turns Create off for both. Joining a running group is always allowed. API and worker read the same variables.
- **A join revives the job.** Every join sends the group's production job again for its current take (same `singletonKey`, `duplicate: ignore`), so a job that paused or was dead-lettered resumes when another person asks, and a queued job is never doubled. A group with no commissioned production (it predates Create) is closed and recreated by `commissionSupply`, not joined.
- **Too many open asks.** A person may have at most 10 asks open (`requested` or `matching`); an eleventh is refused as `too_many_open` (HTTP 429, no receipt) until one ends or is cancelled. Each open ask polls through its own jobs, so the number is bounded. The Planner's demand is not counted.
- **Planned demand is for something new.** When a planned demand resolves, content binds only if the person has not met its explanation, re-derived at that moment under their personal scope from their exploration snapshot. Without proof of what they met, nothing binds. An ask the person made themselves has no such filter: reading a Scroll does not make it unavailable to them.
- **Research blips are not verdicts.** A transient research failure (`dns_timeout`, `request_timeout`, `network_failed`, `http_refused`, or an error that is not a refusal) leaves the job at `research` with no take spent and fails the delivery so the queue retries. Only a verdict about the sources (`soft_404`, refused host, unusable page) or the answer rejects a take.
- **Unsent attempts are not lineage.** A paused run leaves attempts that sent nothing (`not_sent`). They stay in the ledger and in the job's receipt but are left out of the proof a published Scroll must show, so a Scroll published after a pause is attributed to its topic and bound to its facets. Four unsent attempts exhaust a step (`attempts_exhausted`) and reject the take.
- **Jobs.** `content.produce-scroll` payload is the recipe, the recipe version and the take. The queue is pg-boss `exclusive` with `singletonKey = recipe:version:take`: one job per take in flight, and a finished or failed job never blocks a new send. Quartermaster sends at priority 10, the operator at 0. The consumer resumes the same business run on every delivery; an attempt of unknown outcome is never resent. A budget or quota stop pauses a run (job open, delivery completes) instead of rejecting the recipe.
- **Bounded takes.** A rejected job is final for its take, but a recipe may be taken again: the job identity is (recipe, version, take) with take 1 to 3. Take N starts only when takes 1 to N-1 all exist and were rejected, never after a published job or an unknown attempt. Each take is a new business run with its own writer run. `produce-library` and Create send the next take of a retryable recipe.
- **Waiting.** Each waiter polls through its own `supply.resolve-request` job every 20 seconds (a delayed job whose ID is per request and slot, so polls never fork) and closes after 30 minutes. Polling reads the recipe's standing, not a take, so a waiter benefits from a later take. The wait ends at once when production ended without a Scroll. A waiter whose group commissioned nothing commissions as if it had just asked. The 30 minutes also applies at read time: an open request past it reads as `could_not_prepare` whether or not a job closed it, and the next write freezes that outcome.
- **Recovering open demand.** `supply recover-open-demand [--dry-run]` sends one resolver job (stable ID per request) for every open ask, so asks that predate Create or lost their poll advance. It prints counts by state, queued and already queued, and calls no provider.
- **Free-text matching.** A free-text ask is stored as `matching` and decided by one role call, `supply.match-request` (`MiniMax-M3.1-Flash`, low effort, one repair), on the personal harness with the request ID as the business run. The answer must be an exact catalogue planet and optionally one of its facets (the schema refuses anything else); `null` closes the ask as unsupported. A match is then treated as the person's own catalogue ask. Limit: the generic personal harness runs only while recording is at its initial generation, as for Jev.
- **Facets by coverage.** A catalogue facet is established by admitted coverage (`content.region_bindings`), not by the discovery projection's own facet labels, which hold the planet ID and never matched a facet ID.
- **Production caps.** The production scope has its own daily caps (`KS_REASONING_PRODUCTION_REQUESTS_PER_DAY` 200, `KS_REASONING_PRODUCTION_TOKENS_PER_DAY` 3,000,000) in place of the per-person scope caps. The global and role caps still apply.
- **Requests list.** `GET /v1/content/requests` returns the person's own asks (not the Planner's), newest 20, each with its current status and a short title (their words, the catalogue topic or the ready Scroll's title). The client shows it at `/account/requests`; the same component can sit in Keep's Requested view.
- **Limits.** No retry command for a closed request (a new ask is the way); no nearest-options list on a closed request; Pause recording blocks free-text matching; Reel production waits for Cutroom.

## D-041 · 2026-10-24 · Reels from Cutroom: one short operator path, with the money rules kept (#240)

The connected commissioning built for #240 (about 9,800 lines, with its tests) was never used and
could not be: it needed a root-owned approval packet, per-script human approvals, a corpus manifest,
funds and sole-writer attestations with expiry, a pool role mapped by OID, a function-definition hash,
and a pool grant capped at 200 cents, which cannot carry D-030's 400. It is removed. What replaces it is
short, and keeps every money rule.

- **Operator commands, no jobs.** `reel check | order | follow | receive | status | write-off | settle`
  in the worker operator. A Reel takes 13 to 41 minutes and the coordinator watches each paid step, so
  each step is a command that can be repeated; nothing waits in a queue.
- **Claim before order.** A paid attempt records the exact request bytes, then claims the whole
  ceiling in the shared pool, then commits a dispatch intent, then sends one POST. The table refuses a
  paid attempt that leaves `reserved` without a claim. The pool's own functions are used as v1 used them
  (`pool_claim`, `pool_settle`, `pool_release`); the pool cap is the one limit on total spend.
- **Never resent.** An uncertain POST is only looked up by request id. A run that exists is adopted.
  When none is found the attempt stays `unknown`; it can be written off (the claim stays open and
  counted) or, with proof (Cutroom answers, has no run, the POST is over two minutes old), written off
  with its claim given back. A retry is a new take and a new request id.
- **Settle once, at the real cost.** The cost is the sum over the chain (an original and at most one
  continuation Cutroom makes itself). A failed run that Cutroom is continuing is not the end. A
  completed Reel is published first and settled second; a Reel that is made but cannot be published
  stays held with its claim open until a person settles it (`reel settle`), except for the engine's own
  failed checks, a media file that is not a Reel and a repeat, which are settled as spent.
- **Budget.** At most 400 cents of new spend (D-030). Pool migration `0005` raises the cap to 1017, the
  617 cents already settled plus 400, after locking the claim table, and refuses a pool unless the cap
  is exactly 700 and exactly 617 is committed. Every order asks for exactly 75 cents, Cutroom's own cap
  for one Reel: Cutroom stops a run at its ceiling after it was paid for, so a lower ceiling can only buy no
  Reel. A paid order also needs a finished rehearsal here whose estimate plus 20 cents (the most real runs
  have run over) fits in 75. Settled cost above a ceiling is recorded as it was.
- **Approval.** A script carries `approvedBy: coordinator (delegated by owner, D-030)`. The owner does not
  approve each script in a pull request any more (D-030); the pool records the same text with the claim.
- **The twin.** A script names the library recipe whose Scroll is its twin. Every claim rests on that
  Scroll at one revision; the order refuses unless that revision is admitted in the ordering world. The
  Reel is admitted in the Scroll's explanation unit and planet, so Explore offers both formats.
- **Repetition.** The three fingerprints of CF-63 are computed from the script (the template fingerprint
  matches v1's `3d8d42d5`). A new script may not share one with the fourteen v1 scripts or with any Reel in
  the ordering world.
- **Receive.** The second world rebuilds the request from the same script, compares it byte for byte
  with the pool's record, reads Cutroom's runs and publishes the same Reel. It claims, sends and settles
  nothing.
- **Kept as it was:** the byte-pinned wire schemas (CF-61), the pinned engine, the GET-only read client,
  the media store and probe, and the importer of the three v1 Reels.
- **Removed:** migrations 0030, 0031, 0033, 0036 and 0039's tables (never populated; dropped by 0053),
  pool migrations 0003 and 0004 (never applied), the Cutroom queues, scopes and settings of the worker, and
  the `cutroom` operator commands.
- **Limits.** Nothing here has placed a real order. The record check is derived from the three Reels v1
  imported; no completed continuation run has been observed, so a Reel from one is the first real test of
  that branch (it is held, not refused, when the record and result disagree). Run ids must be UUIDs, as
  every real run has been.

## D-045 · 2026-10-24 · Native persistent storage and the lane's journeys (#249)

- **One synchronous port, encrypted underneath.** The account scope's `KeyValueStore` stays synchronous. On native it is now `createSecureKeyValueStore` over `expo-secure-store` (Keystore on Android, Keychain on iOS): memory is the working copy, a restart reads persisted keys back, and changes reach the backend through one ordered queue. The earlier work-in-progress branches rebuilt the scope around asynchronous "prepared" stores (about 800 lines plus changes to `AccountScope`); nothing in the product needs that, so it was not reused.
- **Bounded, and honest about durability.** At most 256 keys and 1 MiB of values; the oldest written go first, and a value larger than the whole budget is not stored. A change is durable a moment after the call, not at it. A backend that fails costs persistence, never correctness. A new key joins the index before its value is written and a value is deleted before its key leaves the index, so a kill in between never leaves a value that purge cannot find. After a failed index read or write the store writes no values, serves from memory, and retries the index at its next read or change, so an unreadable index is never overwritten.
- **Purge.** A scope still ends and purges its prefix (sign-out, account switch, Clear, account deletion). Because a native store outlives the process, mounting a scope also removes every other scope's keys (`purgeOtherScopes`), which cleans up a run that was killed mid-scope. The web keeps its shared `localStorage` untouched: other tabs may hold a scope. The deletion receipt id lives in the same store outside any scope, so it survives a restart and a sign-out.
- **Backups.** `expo-secure-store`'s config plugin is now listed in `app.json`, which excludes its preferences from Android backup (restored ciphertext without its Keystore key is unreadable).
- **Native sign-in binding in the lane, not on dev.** The test API sets `KS_NATIVE_SIGN_IN_BINDING=1`; dev and stage stay unset until the native app ships (the identity README's N1 conditions still hold). The native client already binds its links; the journey uses a mailed link read from the fixture mail file, not an operator link: a native link needs its verifier, and operator links carry no binding.
- **A test API in the emulator job.** The default `api_origin` of `native.yml` is `http://127.0.0.1:3399`, reached through `adb reverse`. A build for that origin sets `EXPO_PUBLIC_KS_TEST_API=1`, which lets the client use plain HTTP (still only to localhost, 127.0.0.1 and 10.0.2.2) and makes the manifest allow cleartext; the APK step checks both ways (allowed in a test build, absent otherwise). The API is the built release trees over a disposable PostgreSQL service, with the authored starter Scroll, one Reel from generated video through a fake Cutroom (labelled "[Fixture]"), and mail recorded in a file. Pull requests carrying `run-native` now build against it instead of the dev origin; an https `api_origin` still builds a normal app and runs only the signed-out flows.
- **Limits.** Emulator evidence only, one AVD. The journey proves restart persistence of the session and of one scope key (the dismissed hint), not every feature that uses storage. iOS is not built. Reading a Scroll gives the Reel/Scroll pair no topics, so no planet forms in the journey.

## D-046 · 2026-10-24 · Content threads, episodes and anchored snippets (#243)

Choices where blueprint §17 and the C04, H01, H03 and X03 artboards leave room:

- **A thread is a conversation of kind `thread`.** It has a root (the exact revision it started from) and a starter. Direct conversations are untouched. A thread never shows in the direct inbox; Talk lists both, newest activity first, from two reads (`conversations/inbox`, `threads/inbox`).
- **Friends are invited, not added.** "Create thread · N friends" (one to eight, all current friends) makes the thread and one pending invitation each. An invited person sees only the invitation (who asked and what it is about) until they join. After joining they read the whole history, including messages from before. An invitation is dated and ordered by when the thread began, never by when the others last talked. Declining ends the invitation.
- **An invitation rests on the friendship that carried it.** The member row keeps that friendship's lineage. Remove, Block from either side, or a new friendship later, end the member's place for them and drop them from the people list; nothing says why. The starter's place has no such dependency. If the person who invited someone leaves or deletes their account, those whose friendship still stands keep their place on their own membership, and anyone whose place had already ended stays out (their membership is closed, so releasing the link cannot give it back). Blocks between two invited members are not looked at: they need not be friends.
- **The thread is its own shared root** (`social_thread`, the conversation row): FOR UPDATE for commands, FOR SHARE for reads, after the personal root and the caller's own account gate. Counters stay atomic SQL, so account deletion tombstones without this lock; it takes the thread rows first, in id order, before touching any inbox head, so it never waits on a send while holding one. Inbox hints go only to members whose place stands and whose account is active.
- **Create is idempotent through the thread's own ID.** It is derived from the starter and the command, so a retry finds the same thread, and receipts live on that root. A refused create writes nothing.
- **Episodes are the declared series that contains the root revision** (`content.series_units`, latest series revision), by part, or the root alone. Corrected and withdrawn units are shown as such and never replaced. "Preparing" and "Suggested" are not produced until What if (#244) exists. "Visited" is the caller's own activated exposure of that asset: their own history, removed by Clear, never a grade, never another person's. There are no thumbnails: the Reel and Scroll have no poster source, so the card is a typographic tile.
- **Which episode is selected, and whether the player is folded, stay on the device** (account scope storage). The server holds no position, selection or seen marker of any member, and no answer has a field for one.
- **Snippets are anchors into the thread's own sequence**, checked against the exact current revision at send. A Reel range is at least one second and inside the duration. A passage is a stable block, a range on grapheme boundaries and the hash of the quote (scroll-model's locators). A block names its id, type and version and may carry a snapshot built by scroll-model; a value the sender typed themselves travels only with `confirmPersonal` (D-006 g). The server copies the quote, the block label and the settings in words when it stores the snippet, and shows them only while the content is not withdrawn.
- **A corrected source is never followed silently.** The card says "Updated". Opening it asks Content: a Scroll passage or block is re-pointed through the explicit anchor map of the two revisions and says so; a Reel has no time mapping, so the card says the moment changed and offers the current Reel, and the old range is never played.
- **Opening or expanding a snippet is not an encounter.** The viewer shows a poster or an introduction with an explicit Watch or Read; only that starts an ordinary encounter of the original content, with its own recorder. "Open as set" shows the sender's settings in memory only and never overwrites the reader's own saved settings.
- **A passage is picked by sentence** (a run of sentences of one block, at most 600 characters), which also works with a keyboard and a screen reader. Mapping a native text selection to offsets is not built.
- **Not built:** What if, perspectives and branches (#244), "Keep listening" (audio only), renaming a thread, adding people later, mute, Like and Save inside the thread's encounter area (they stay on the full-screen encounter), the multi-pane desktop thread (D03), a snippet's own link, and reporting from a thread.

## D-047 · 2026-10-24 · Sharing & visibility, availability and the friend visit (#241)

Choices where blueprint §17 to §19, D-006 e, D-027 and the F01, F02 and U06 artboards leave room:

- **Everything starts off.** Nobody may visit, no system is shared and availability is hidden. A person who never opens F02 has no row at all, and reading the settings writes nothing.
- **Visitors see systems and their planets, nothing else.** A shared system shows its name and its factual planets' names. Stars, regions, routes, hypothetical places, activity, positions, sizes and any count of what is hidden are never published. A hypothetical system is not even offered. Labels are the person's own words and must pass the public-label rule.
- **Public identities are random and short-lived.** Each shared system and planet gets a random ID that stays while it stays shared and is new when it is shared again, so two shares cannot be linked. The list is sorted by label, so its order says nothing about when anything formed. The visitor's device invents the map's positions, family, colours and seeds from the public IDs alone (`visitor-scene.ts`); the owner's anchors, seeds and families never leave.
- **A published copy, not a read of the owner's Geography.** A visitor's request never enters the owner's personal root (lock order, blueprint §19). The owner's own command (`visibility.set`) draws the copy from their Geography in the same transaction. The worker redraws it after each scene projection (system actor, its own transaction; a failure retries the job, which re-projects nothing). A universe that shares nothing is a no-op.
- **Revocation is the very next read.** Every visit read checks, under the friendship's lock, that both people are friends and neither blocks, that the owner's audience includes the visitor, and then reads the copy. The client rereads every 15 s while the screen is open and drops the list after two minutes without an answer, so going offline cannot hide a revocation. There is no socket hint for it.
- **One refusal.** Never shared, no longer shared, an ended friendship, a block, an unknown person and yourself all give the same `unavailable` answer. The screen says "stopped sharing" only from the visitor's own memory of having seen the list in this visit, and then promises that nothing is kept: the list lives in memory and goes with the screen.
- **The contract changed where it was only declared.** The visitor answer carries the visitor's `pairRevision` and the copy's `publishedProjectionRevision`, which is a random token that changes when the list does and counts nothing; the owner's settings revision never leaves the owner (the declared `visibilityRevision` and the `expected` input are gone). The answer lists planets under each system. The owner's own read lists their systems with a `shared` flag instead of `sharedSystemIds`, so one read draws F02.
- **A choice of friends lasts as long as the friendship.** The chosen-friend rows are deleted when a friendship begins or ends (accept, remove, block), under the friendship's lock, so an old "may visit" cannot return with a new friendship. "Friends I choose" with nobody ticked is saved as nobody and stays selected on the page.
- **Availability is a heartbeat that lapses.** The app sends `presence_heartbeat` over the socket every 20 s while connected and visible. The answer is always `{ ok: true }`. A beat is stored only for a person whose preference is not hidden, and hiding deletes the row. "Online" lasts 60 s (three missed beats), "Recently active" up to 15 minutes, and the preference caps the word (someone who chose "Recently active" is never shown "Online"). The answer carries a constant lease (30 s or 60 s), never the time left, so the last beat cannot be worked out. Beats are stamped, and their age measured, by the database clock. `expiryRevision` is a random token, new for each stretch of activity, so a friend cannot learn how often someone has been around. Hidden, expired and unknown share one wire shape. Friends read it on the friends page and the pair read (no new route); the client rereads every 20 s while Friends is open and keeps only words, each for its lease counted from when the read started.
- **Visiting is only a read.** It writes no row anywhere, tells the owner nothing and is no evidence for either person. A test compares the row counts of every table before and after.
- **Erasure.** The published copy is universe-keyed: Clear and full erasure delete it, so a friend who visits after a Clear sees an empty universe (P02) while the person's choices stay. The settings, chosen friends and heartbeat are account-keyed: Clear keeps them and deleting the account removes them (the chosen-friend rows on either side). The export says in words who may visit, how many friends were chosen (never who), the availability word and the titles of shared systems; never a heartbeat, a public ID or another person.
- **Not built:** F02's "Preview what Ravi sees", entering a room from a visit (there are no rooms), availability on Talk rows and in the share sheet, a live revocation hint, and region cards on a visit.

## D-049 · 2026-10-24 · What if, Another perspective and the shared Scenario Planner (#244)

Choices where blueprint §14, §16, §17 and the X01–X04 artboards leave room (D-006 a, i, s; D-037; D-046):

- **A new module, `scenarios`, owns the exploration.** It has `scenarios.nodes` (the branches of one thread) and `scenarios.drafts` (a member's request while directions are proposed). Social still decides who may take part in a thread: scenarios enters a thread only through Social's `THREAD_GUEST` (enter as a member, read a bounded window, keep receipts, announce), and workers read standing through `READ_THREAD_STANDING`. Content produces the Scroll and Quartermaster commissions it; neither reads scenarios' tables.
- **A branch is a node in a tree, one parent each.** The parent is the thread's root revision or another node at a revision. A **What if** carries explicit changes (one or two) and what stays the same (up to three); the premises that hold are the parent's plus these, at most four, and a node that changes a subject its parent already assumes replaces it. Code checks this with one pure rule (`planStep`), used for the model's proposals and for a member's own words, so anything the model proposes can be chosen. A line the step keeps may not name a subject an earlier branch assumes in other words (`kept_contradicts_premise`); one that restates it in the same words adds nothing, and is listed once, among the assumptions. The member's own form lists what already holds and lets each changed line either add a premise or name the one it replaces, and an edited suggestion keeps its subjects, so a new line never silently stands beside the one it contradicts. **Another perspective** has a named lens and changes no assumption; it keeps the parent's. A branch is hypothetical if its parent is or if it is a What if, and that status is inherited by every descendant. A perspective on the unchanged root is not hypothetical.
- **The Planner only proposes; the member's choice is the only thing that commissions.** Asking (`draft`) stores a private draft and sends one job; it never starts production. The role `scenarios.planner` (version `planner.1`, MiniMax-M3.1-Flash, one call and one repair, low effort) sees the member's words, the subject, the premises that hold and the last 12 messages of the thread, clipped, with authors as "you" or "member": no names, ids or other threads. It answers one clear idea (`direct`, one option) or two to three directions (`options`), each marked if it needs confirming (a speculative or unclear premise, X01's third state). The run is the draft's ID, so a redelivery never pays twice. A member may instead write a complete request of their own (also while the directions are still being thought of); that needs no model. At most 20 drafts per member per UTC day; a draft lives two hours.
- **Choose is one idempotent command.** In one transaction under the thread's lock it checks membership and the parent's revision, makes the node (or finds the live one with the same meaning, that is the same parent, kind and change or lens, which is reused and says so: two members asking for the same idea share one branch and one Scroll), and commissions exactly one order through Quartermaster. That order has its own ledger (`supply.scenario_orders`) and does not go through ContentDemand's compatible-supply matching: matching exists to join a request to supply for the same brief, and a branch is the opposite, a Scroll made for one thread and its premises, never joined or reused. A retry, or two identical commands at once, make one node, one order and one job. A late model result for a member who has left, or a draft of a member whose place ended, is dropped. A parent that changed since the member looked is `stale_revision`; a removed parent cannot be continued.
- **Quartermaster's Create for a branch is a made-to-order Scroll.** The order is its own work (never joined, never reused for another thread): recipe key `order-<node>`, a code-built brief, and up to three research pages chosen by code from the root Scroll's own provenance (falling back to the same explanation's other Scroll, then the library recipe's pages). It uses the same `content.produce-scroll` job, take and stop rules as a library recipe. The brief holds the direction's title and explanation, the premises and what stays the same (a premise may be a sentence the member wrote themselves), and the public title and summary of the subject; the free text they typed to ask is not in it. The writer is told the mode (`scenario-writer.v1`): a thought experiment that opens by stating the premise ("Suppose …"), marks every consequence as reasoning, writes premise quantities in words, sets the changed world beside the original and ends with a limit; a perspective keeps the same facts and changes the emphasis. The kicker and the framing (a **Hypothetical** label with the premises, or the lens) are copied by code, never written by the model, so a branch below a what-if carries the label and the whole premise.
- **A hypothetical Scroll never grows real-world coverage.** An ordered Scroll is published with no topic attribution and no coverage (`attribution: none`), so it adds no planet, no region, no discovery lane and no progress. It is excluded from every discovery candidate lane, cannot be shared as a link card, and is reachable only by members of its thread. Content asks the ordering module on every way in by ID: open, document read, save, like and hide, navigation (a `return` to it, an offer of it, activating an offer, an exposure's context), a snippet that names it (sent or opened), the saved list and saved page (an entry the caller may not see reads as withdrawn, with no title or summary, and can still be removed) and the person's data export (it keeps no title, place or part: the line reads "Withdrawn"). IDs compare in lower case, so a shouted ID is the same ID. Every ask reads on the caller's own open transaction (`ReadOn`), never a second connection, because the pool is small and a second connection per concurrent open would exhaust it. So a member who leaves loses the Scroll everywhere, while its owner's other Scrolls are untouched.
- **Preparing is honest, ready is a fact.** A node is `preparing` until its Scroll is admitted, then `ready` and bound to that asset revision; `failed` when production stopped or 30 minutes passed. A worker sweep (`scenarios.resolve-branches`, every minute, idempotent) binds, sends the next take of a rejected recipe (at most three), closes, and tells the thread's inboxes. The cards poll every 5 seconds while one is preparing, and a hint also refreshes them.
- **Two caps bound the spend**, counted from Quartermaster's own ledger of orders: `KS_SUPPLY_SCENARIO_DAILY_CAP` branches per UTC day for the world (default 20 in `local`, otherwise 0; dev 6) and `KS_SUPPLY_SCENARIO_THREAD_CAP` per thread over its life (default 6; dev 6). A refusal is `budget_unavailable`, writes no node and tells the member plainly. Only the API reads them.
- **Removing a branch** is allowed to the member who started it, at the revision they saw. The card stays in the chat where it was, as a quiet "removed" note, so the tree has no hole, and its Scroll is closed to everyone; the Scroll is not deleted and a production in flight is not recalled. The same idea can be asked for again later. Descendants keep their premises.
- **Erasure, exactly.** A draft (the member's own request text and the directions proposed) is private: erased on Clear, on universe erasure and on account deletion. A node is shared work of the thread, like a message that others have answered: kept on Clear. On account deletion only the link to the person (`started_by_account_id`) is cleared. What stays, without any account ID, is what the others read: the card's title and premises, the order's brief and framing, and the Scroll; a premise the member typed themselves is among it. (Messages are tombstoned on deletion, D-043; a branch's Scroll has been read by others and cannot be unwritten, so it is treated as thread content, not as the person's message.) The member's receipts for these commands are deleted with them on account deletion and kept on Clear. The export lists their requests and the branches they started with their premises. The planner's run and its protected bytes follow the reasoning harness's own retention.
- **What this changes.** D-046 said the episode states Preparing and Suggested wait for What if. Branches appear as cards in the chat; the episode navigator is unchanged until X03.
- **Not built:** Reel branches (a branch is a Scroll), a retry command for a failed branch (remove it and ask again), the sequence view and history map (X03, X04: PR 2), branching from idea rooms (#245), branches whose root is a corrected revision (the member asks again from the current one), and a push to someone who has not opened the thread. A member whose recording is paused gets "no directions this time" from the Planner and can still write their own.

- **Sound.** A mute switch sits at the end of the progress row. Sound is the person's choice, never a side effect of a tap.
- **No topic chip.** The offer carries no topic, so none is drawn. API gap: `EncounterMetadata` would need a `topic` field. Likewise a Part is labelled "Part 2", not "Part 2 of 3": the series total is not in the context.
- **Edge tabs are buttons, not links.** The artboards call them real links; they have no address of their own (a continuation is an in-session move with an expected link, not a route), so they are named buttons with the destination in the name. Keyboard and screen readers reach them like any control.
- **Continuation.** A ready next Part is the yellow edge tab; a ready related move is the dashed tab; the previous step is the ink tab on the start edge. A Scroll has no edge tab: its continuation is the end-of-article card and ⋯. Blocks own horizontal drags there, and vertical reading never navigates.
- **Format switch.** A missing sibling shows its plain name and opens the request sheet (E06); a requested one shows "preparing". The ready notice offers Later and Open and never switches by itself.
- **Ending (E08).** A stop from the thread or from an exhausted direction is the yellow card: Keep a way back, Something different, Done for now. Keep a way back asks for a save and then confirms, with See it in Keep and Undo (Undo is the existing five-second removal). "Something different" opens a fresh subject: there are no suggestion cards because the Composer offers one subject at a time. Done for now is a calm Explore, nothing playing.
- **Share (H01 so far).** Copy link and the system share sheet, for the encounter's own address (`/reel/<id>`, `/scroll/<id>`: admitted shared content only). No friends, conversations or moments until those exist.
- **Keep.** One card per item: tile, format tag, title, one line of place ("Paused at 0:31", "Your place is kept", "Not started"). A visible Remove stands in for the swipe. The Requested filter is not drawn: there is no durable request list. Paging keeps its own buttons.

- **Entry.** "Continue with email" is cobalt and "I have a sign-in link" the quiet outline (A01 as drawn); the placeholder row stays out.
- **Overlays on the web** are drawn into the document body so they sit above the tab bar and rail.
- **Sheets are not departures (D-006 k).** Closing a sheet over a playing Reel plays it on from where it was (`entry.resumePlaying`, read once by the remounted player); Back, a trail jump or a tab detour still return paused. A sheet action that navigates (Account, a conversation) waits for the browser Back that removes the sheet's history marker (`afterPendingBack`; the encounter marks that Back as pending), and the marker is popped once however many state changes land first.

## D-052 · 2026-10-24 · Personal model runs: one paced run, a valid answer applies, budget ends a run (#231)

On dev, one test account that read every 15 s started 229 Cartographer runs in five hours. 228 were cancelled and one completed. 94 made a model call (about 940k tokens): 41 got a valid answer that was then discarded, and 53 failed `OUTPUT_SCHEMA_MISMATCH`; 46 of 51 first answers failed validation. Once the person's day of tokens was spent, 138 admissions an hour were refused. A Planner run stayed `admitted` in the ledger with no attempt, revived by every encounter. This changes D-035 ("Stopped runs start again", the budget part) and D-038 ("one run and one model call per material change"). Rules:

- **One pending run, paced.** Evidence already coalesced into one active run per person and role. A run that settled used to start its successor at once, and evidence after it started a run at once. Now a settled run sets `next_run_not_before` on the role's state row (Cartographer 30 s, Planner 5 minutes, migration 0060) and the next run's wake waits for it. Evidence meanwhile joins that run, which freezes its context when it starts, so a newer input supersedes only before dispatch.
- **A valid answer applies unless authority changed.** An answer in flight is not voided because more reading arrived. Cartographer: every operation is checked against today's authority; withdrawn, corrected or retracted support still makes it `source_changed`. Planner: every opportunity is checked against today's evidence and inventory; a new explicit intent still makes the plan stale. The other reasons stay: epoch or recording revoked, the geography revision moved, the role switched off. A valid answer that concludes nothing needs changing completes its ledger run; only a voided one is cancelled.
- **No model call without a decision for it.** Rules form places (D-038). A reading-triggered Cartographer run with no place due asks no model: the run settles `insufficient/no_changes` with no ledger run, and activity changes alone apply by the rules. Routes and labels are the model's to propose with the places that form.
- **First answers validate.** The role never named the `version` it must return, the repair printed the allowed literal as `?` (a model answered `"version": "?"`), and a planet needed supports the model had to work out. The role now shows the reply shape, lists what the rules entitle as ready `due` operations, and a repair names the operation and the rule it broke. The model is asked only for what it adds: another canonical label for a due place, a route, a label revision. Code applies every due operation whatever the model returns (`reconcileWithRules`), so the model does not copy every 72-character `supportRef`. The role judges the model's list with the due operations merged in (`mergeWithRules`), so a route to a planet that is only due is valid; a finding on a code-owned operation is not the model's to repair, and the rules are then applied alone. For a reader owed many places that copy could exceed the 8,192 output tokens and fail the repair the same way. An empty answer is the normal reply and is recorded `applied_with_rules` (a valid proposal plus the rules); `applied_by_rules` stays for no usable answer. Real calls: first answers invalid 3 of 3 before, 0 of 11 after (0 of 5 with the final wording, three of them empty).
- **A context that no longer hashes the same retires its run.** The `due` items change the model-facing context, so a run claimed before a deploy no longer matches its recorded hashes and could never send. The claim used to return silently and the run held the person's scope. It now retires such a run (`stale/context_changed`) when accounting shows no live attempt, and starts an unpaced successor. A run with an attempt in flight is left to the ledger's own recovery.
- **Budget ends a run.** A Planner run refused for budget or the failure brake closes its ledger run `cancelled`, ends `insufficient/budget_exhausted` and is not revived; the next evidence starts a new run, paced. The Cartographer already applied the rules and closed its ledger run. A run whose ledger run was closed under it ends the same way and a new business run takes over.
- **Idle admitted runs are closed.** The five-minute sweep also closes personal runs left `admitted` for six hours with no live attempt (`reasoning.idle_runs_closed`). Their owner finds the run closed and starts another. `reserve` refuses a run that is no longer `admitted`, because the sweep takes no personal root lock and can close a run between admission and reservation.
- **Explicit requests are a latent operator path.** `REQUEST_CARTOGRAPHY` and `REQUEST_PLANNER` have no product caller today; only tests use them. A request is not paced, it asks the Cartographer's model even with nothing due, and it joins a pending run instead of starting a second. The Cartographer reads the explicit mark from the person's latest desired source when it claims the run, so reading that arrives before the run starts overwrites it and the run may skip the model. A plain request accepted while a Planner run works does not void that plan; it gets a paced successor.
- **Budgets unchanged.** The per-person day stays 60 requests and 600k tokens. A Cartographer call costs about 10k tokens and a Planner call about 6k; with the rules above a 30-minute session uses about 70k. The dev exhaustion came from the churn, not from the cap.

## D-053 · 2026-10-24 · Desktop layouts and accessibility checks (#247)
