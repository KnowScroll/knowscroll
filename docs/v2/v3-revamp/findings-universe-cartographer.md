## 2. Cartographer and formation today

**Who decides.** Code forms places (D-038, README `modules/geography`); the model (`geography.cartographer` role, `KS_CARTOGRAPHER_ENABLED=1` on dev) may only add another canonical label for a due place, a route between two formed planets of one system, or a label revision. `requiredChanges` (`domain/formation.ts`) is applied whatever the model returns (`reconcileWithRules`). Outcomes recorded on the run: `applied`, `applied_with_rules`, `applied_by_rules`. Policy `geography-passive.v1` (`domain/policy.ts`): `systemUnits 2`, `planetUnits 3`, `planetFacets 2`, `quietAfterDays 30`.

**Inputs.** Evidence qualifies a Scroll reading (`modules/evidence/domain/policy.ts`, q >= 0.6, coverage >= 0.5, block dwell). Personal Context projects it; Geography reads only *trusted coverage* of (topic, facet, `explanationUnitId`) triples via `readTrusted` (`application/context.ts`). Reels give dust only until Reel facet coverage exists. Unit = canonical explanation unit; Reel and Scroll twin, variants and replays count once. Likes, quizzes, visits, shares count for nothing.

**The catalogue is the whole geography vocabulary.** `CONCEPTS` (`content/domain/concepts.ts`, derived from `content/domain/library/*.ts`, version `content-concepts.v1`) = 6 systems (earth, space, machine-learning, human-body, computing, history), 17 topics = planets, 52 facets = regions (3 per planet; the one History planet has 4). Candidates (`candidates()` in `application/context.ts`) are generated from it: system + star per root topic, planet per child topic, region per facet. No free-form place can exist. Names: `label(conceptId)` = last id segment, capitalised ("Axial tilt"), or the catalogue meaning sentence; the model can only choose between them. So **a region's name is public catalogue text, but its existence for this person is private**.

| Kind | Forms when | Source file |
|---|---|---|
| Dust (not a place) | >= 1 qualified unit under a topic of a system that is not established | `domain/emerging.ts`, `ReadOwnEmerging`: opaque UUID per catalogue system, hash of universe+epoch+system, max 16, no label/count |
| System + star | >= 2 distinct qualified units under any topics of that system | `formationEligible` |
| Planet | >= 3 units over >= 2 facets of that topic, parent system exists | same |
| Region | >= 1 unit on that facet, parent planet exists | same (`units >= 1`) |
| Route | model proposes, both planets supported, same system | `proposalIssue` |
| Quiet | latest support more than 30 days before evaluation | `activityFor` |

**Geometry today.** None in Geography. Scenes (`modules/scenes/application/projection.ts`) gives each object, once and forever: `seed = hash(policy, private world seed, objectId)` (32 hex, deterministic and stable), `family` and `palette` from the library plan (`sceneFamilyOf`: terraced/ridged/archipelago -> ochre/sage/cobalt), and a lattice slot (32x32, 300 units, nearest free to parent). Slots are allocated in topological creation order and never move. Chunks: <=100 objects per system. The client then **re-derives** layouts from anchors only coarsely (`composeSystem`: orbit band by distance, angle by direction) and region pins from a hard-coded 9-spot table in creation order (`composeRegions`, D-039). There are no region borders, continents or loops anywhere today, and no persisted "type", "rings" or "moon".

**Pacing and state.** D-052: material change from Personal Context (`GEOGRAPHY_MATERIAL_CHANGE`, in the evidence transaction) records a desired revision; one run per person; `next_run_not_before` 30 s after a run settles (`domain/pacing.ts`); a reading run with nothing due asks no model; model budget is a background share (D-058). Each applied delta publishes `UniverseDelta` ops and `GeographyApplied` -> `scenes.project` job + U05 formation facts (once-per-formation claim/ack, `scenes.formation_presentations`).

**Emerging.** Read-only dust (`/v1/universe/emerging/read`), client `universe-dust.ts` re-reads when the geography revision changes and on foreground; drawn as `DustGlyph`; position from the opaque id (`placeDust` in `universe-layout.ts`). Never a nav target.

**Landmarks.** Not a backend concept. The lighthouse/harbour glyph on a planet is client decoration from the planet seed (`planet-scene.tsx`). The new design does not contain it.

**"You were here" / ship / Lately / absence.** All device-local, none server-side: `universe-here-marker.ts` (region id, 14 days), `universe-memory.ts` (camera, Lately flag, `lastPlace` = ship, `seenAt`, `ABSENCE_MS` 3 days). Map browsing writes no evidence (verified: handover J3 "Map browsing writes no evidence"; the region card calls `/v1/experience/region/preview` which is a read; only an explicit Open starts a real encounter through the encounter engine).

**Rooms and stations.** `RoomStation` read (`/v1/rooms/stations`): station sits beside a system (and planet) of the caller's own map; client places it by room id hash (`stationOffset`). Rooms read Geography through `READ_GEOGRAPHY_SCENE_INPUT` (D-051).

**Visits (D-047, `contracts/sharing.ts`).** Owner publishes a *separate copy*: systems and their planets, labels only, with random public ids; **no regions, routes, stars, activity, positions, sizes, seeds, families or hidden counts**. The visitor device invents positions/family/colours from public ids (`apps/client/features/visit/visitor-scene.ts`, pure, hash-based). This is the repo's precedent for deterministic client-side derivation from stable ids.

**Privacy filtering.** Scene reads are caller-only and never expose the world seed or Geography context; stale reads cannot relabel; Clear removes everything and advances the epoch (Scenes erased before Geography). Hypothetical places (What-if) are separate objects with `truthStatus`, never formed from passive reading (`formationEligible` rejects non-factual).

**Two gaps found in today's code that matter for the revamp**
1. **Quiet is never computed without reading.** `set_activity` is produced only inside a Cartographer run, and runs start only from `GEOGRAPHY_MATERIAL_CHANGE`. There is no cron on geography (schedules exist for feedback, identity, scenarios, scenes recovery, reasoning only). A person who stops reading for 60 days still has every place `active`. The integration test (`cartographer-formation.test.ts` line 227) runs `cartograph` manually after ageing the data. Lately and "Everything is where you left it" therefore need either a sweep or a read-time derivation.
2. **Activity is per-place stored state with a 30-day window** and is also present on the visitor-excluded wire. A shorter "Lately" window would need a second signal.

**Rules for all five animations (Animations page).** One time value `t` drives everything, advanced by elapsed time and clamped to 0.1 s per frame. Each starts and ends exactly on a final screen; the tab bar never moves; destination chrome rises in last; a tap ring marks the tap that starts it. Reduced motion and Simple drawing play none of them. Taps are ignored while one plays, and Back jumps to the end frame. Going back up is not designed (a 0.3 s cross-fade until it is). Search and orbit dial jumps use the same animation for the same step down; long jumps across levels go straight to the destination. Desktop D02 has none.

## 5. Algorithm changes the Cartographer needs

Short answer first: **formation itself does not change.** Systems, planets and regions keep forming from the same catalogue and thresholds. The changes are in what Scenes persists next to each place (type, haze, site), one new background signal (quiet without reading), and how the client derives geometry.

**(a) "Not yet reached" regions, without leaking names.**
- Source today: a region is a catalogue *facet* of a formed planet (`CONCEPTS` in `content/domain/concepts.ts`). An unformed facet is simply a facet with no qualified unit. The catalogue is code-owned and identical for everyone, so its *count* leaks nothing about the person; its *names* are the sensitive part (naming a facet tells the person what to read next, which also breaks "uncharted never written"). The Planner must not feed this: its plan is a set of suggestions and "never forms a planet" (planner README); using it would turn suggestions into map content.
- Options: (1) **Decorative only**: a fixed number of grey masses from the planet seed, as the design file itself does (`explored` vs `locked` counts are constants in `mapWorld`: 2 of 5, 4 of 7). Zero wire change, zero leak, but "they unlock on their own" is then fiction. (2) **Exact sites** (recommended): the planet descriptor carries `siteCount` (= its facet count) and each region descriptor carries `site` (its facet's ordinal in the catalogue, 0..K-1). The client lays out K cells from the planet seed; cells whose site has no region are grey under cloud, unlabelled, absent from lists, search, outline and the accessibility tree. No names, labels or "N left" text ever cross the wire, and a region turns colour in place when it forms. Add decorative grey continents on top so the visible grey count never equals the unformed count exactly.
- Catch: D-026 says no client-invented region offers; grey cells are not offers (no target, no tap action). Keep them non-interactive.

**(b) Stable geometry: client-side seeded generation, not stored.**
- Recommend: **deterministic client generation from persisted seeds** with a pinned generator version, exactly as blueprint §13 says ("server stores semantic/visual descriptions; clients generate detail") and as `visitor-scene.ts` and `scene-core` do today. Do not store contours on the server (17 planets x thousands of points, chunk caps 256 KiB, immutable versions would balloon).
- Move the generators (`rng`, value noise, `placeConts`, `buildWorld`, marching squares) into `packages/scene-core` so server tests and web/RN share one pinned implementation. **Replace `Math.sin/cos` with scene-core's pinned quarter-circle table** (README: "no runtime trigonometric functions can vary across engines") or Hermes and V8 may draw slightly different borders.
- **Stability bug in the design's builder**: `buildWorld` seeds regions from `P.regions.length` (`a0 + q*TAU/k`, `perCont` = `[n-1,1]`), so adding a region moves every border and label. That violates "positions and names stay the same". With option (a)(2) the fixed site table makes cells independent of how many have formed (Voronoi over all K sites from the start); formed cells never change shape.
- Persist a generator version on the descriptor (`worldmap.v1`) so an app update cannot remake worlds (blueprint §13). Cache built worlds per `planetId + generatorVersion`; build lazily off the render loop (about 25k grid cells per world).
- Globe and landed map use different noise tags in the design, so they are two drawings of one planet; regions must still be the same sites in the same order.

**(c) Planet type: six types, 17 planets on dev.** The Rules page says a type never repeats in one universe. The catalogue has 17 planets (up to 17 can form for one person), so the rule cannot hold. The design's own demo falls back to `order[0]` (a repeat) when types run out and the Space-views file lists 8 types while the rest list 6.
- Options: (A) **Unique until exhausted** (recommended): assign by creation order, least-used type first, preferring a type not already in the same system; the first six planets are all different. Repeats get a different hue shift (`d` in the genome), continents and cloud layout, so repeats still look distinct. (B) Unique per system only (library has at most 4 planets per system, so six types always suffice); adjacent systems may share a type. (C) Add types (the space file already has `toxic`, `exotic`: 8 total): still fewer than 17. (D) Cap planets at six: breaks the catalogue and formation rules, not recommended.
- Assignment must happen **once and be persisted** (or be a pure function of immutable ids), never recomputed from "what is used now", which is what the demo `genome()` does and which reshuffles on reload. Order key: formation order. UUIDv7 `objectId` order is formation order in practice (ids are minted in the context of the forming run; D-039 already relies on it for regions) but not formally guaranteed; persisting at projection time is the robust option. Scenes already allocates slots in topological creation order, so the hook exists (`projection.ts`).
- Stored look fields (`type`, `rings`, `moon`, `haze`, `site`) cannot be added to existing rows silently: `scenes.guard_object` (migration 0027) freezes everything in `payload` except `descriptor.label` and `descriptor.activity`, and descriptors are strict `scene-descriptor.v1`. So: a new descriptor/generator version, a capability string in `SceneClientCapabilities`, a migration relaxing the guard (or a sibling `scenes.looks` table, simpler and keeps v1 objects immutable), and an authorised backfill for existing dev worlds (README: "reads and migrations never bootstrap" worlds).
- Stopgap if the owner wants UI first: derive type client-side from `objectId` order (zero contract change), with the generator version pinned in client code. Flag it as temporary; it breaks the "pin generator versions" rule.

**(d) System family (haze).** Six systems on dev, six haze families: give each `LibrarySystem` a `haze` in the code-owned library plan (same place as the existing `sceneFamily`), project it onto the system descriptor once, never change it (same rule as `family`). Colour only the halo (design: "Suns are always orange"). Visits derive haze from the public id, as `visitor-scene.ts` does for family today.

**(e) Quiet, Lately and "Everything is where you left it."**
- Existing signal: `set_activity` active/quiet from "latest qualified support under the place older than 30 days" (`activityFor`); inactivity never removes a place. Good and consistent with AGENTS ("Inactivity changes activity, never existence").
- **Gap**: it is only recomputed inside a Cartographer run, and runs start only on new material evidence. A person who reads nothing for 90 days never sees anything go quiet. Fix (recommended): store `next_quiet_at` on `geography.state` (min over active places of latest support + 30 days) at each run; add a cron-scheduled job (like `scenes.recover-formation`, every 5 minutes, or hourly) that finds states with `next_quiet_at <= now()` and records a material change without model use. A run with no place due already "applies activity by the rules" with no model call. Cost: one indexed query. Keep a boolean on the wire (no timestamps, so nothing about reading rhythm leaks).
- Whether the Lately window should equal 30 days is a product question (owner Q 6.4). A shorter window needs a second stored state or a read-time derived flag.
- "Everything is where you left it." needs no backend: device-local `seenAt` (`ABSENCE_MS`, 3 days) already exists. Show it when Lately is on and the person was away.

**(f) `sel`, "Return to <planet>", route, and evidence.**
- Today `youWereHere` (region id) and `lastPlace` are device-local in `scope.storage`, purged with the scope. Keep that: navigation memory, not evidence, never sent. Per-planet `sel` = a small map `{planetId: regionId}` in the same storage; cap its size; drop ids that no longer exist (the code already validates a saved camera via `cameraStillValid`).
- `route` is a Cartographer route to another planet of the same system, shown as a chip with the destination planet's name. It needs no change: the relation exists, only the line goes.
- **Map browsing still writes no evidence.** Confirmed: map reads are read-only POSTs (geography, scenes, emerging, region preview); only the explicit Open on a region card starts a real encounter through the encounter engine (D-039, handover J3). The 3D renderer must keep it that way: camera, fly-in, search, dial and ship animations call no write endpoint. Add the existing "no writes while browsing" integration check to the new slice.

**(g) Rooms per system, stations, the ship.**
- Rooms: `RoomStation.placement.systemId` (and optional `planetId`) already gives "rooms per system"; the "With rooms" filter, the "1 room" meta and the 3D station all come from the existing `/v1/rooms/stations` read. A room whose topic is not on the person's map has no station (as now). No visitor stations.
- Ship (U02): in the file it is a small rocket parked on a planet, absent in Lately and for visitors, and the entering animation ends with the rocket parked there. It represents **where you were last**: today's `lastPlace` (device-local, "the last system, planet or region the person flew to"). The sample parks it at Attention in the overview and at Inference in U02, so the design does not say whether it is "last planet entered" or "planet of the last region opened". Recommendation: the planet that contains the last place (the region's planet for a region). It is not a person, a friend or live activity.

**(h) Emerging dust vs pacing.** No change. Dust is a live read of Personal Context (not paced); the first system forms only after two units and the next Cartographer run (up to 30 s wait, D-052). So dust appears straight away and can sit for a while before the sun lights. The client already refreshes dust when the geography revision changes and on foreground. U01 Emerging maps to: no systems, at least one cue. New work is only drawing (`toonNebula`) and sizing one nebula for one cue. If the formation run is slow (budget exhausted: rules still apply), dust stays; nothing is promised. Keep dust unlabelled and uncounted.

**(i) Search over names on device.** The client already holds every established place label in the scene chunks (`placesOf`, `universe-search.ts`). Needed: add rooms (title from the stations read), the kind and mono path (`placeTrail`), best-match ordering, and fly-to via the 3D camera. Nothing new from the server. Unreached cells are not objects, so they can never be searched. Do not log queries; keep search out of the oRPC layer.
