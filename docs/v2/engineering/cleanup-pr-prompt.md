# One repository-wide KnowScroll cleanup PR

Copy the following brief into a fresh coding session.

Open **one PR against dev** covering the full KnowScroll repository: remove demonstrably unused code, improve developer comments and rewrite contributor-facing READMEs in plain language. Work through the entire inventory in this session or continue on the same branch after handoff. Keep related edits together in small commits inside that one PR.

1. **Set up.** Read AGENTS.md. Fetch origin/dev and start a dedicated issue branch/worktree from that revision. Use pnpm issue-context to find or create one cleanup issue. Keep one short checklist in its body or the PR describing areas covered, remaining work and verification. Open your PR with `gh pr create --base dev`.
2. **Inventory the whole tree.** List tracked apps, packages, backend modules, migrations, tests, scripts, operational tooling and their READMEs. Include contributors' web, native, API, worker and operator entry points. Start with Account as a worked example, then continue through every area. Mark each reviewed area as changed or already clear, with a brief reason. Read source and decisions by area to keep each pass focused.
3. **Remove unused code with proof.** Use Knip, import/reference search, package exports and tests to find candidates. Trace Nest registrations, pg-boss job names and schedules, platform file variants, Expo file routes, public HTTP/CLI contracts, older serialized records and dynamic lookups. For each deletion give its former purpose, the caller check and a regression check. Preserve used compatibility paths, migrations, pinned vendor/design files and fixtures that exercise supported behavior. When evidence is incomplete, retain the code and record the open question.
4. **Write comments for a human.** Prefer intent-revealing names for simple code. At important boundaries explain who calls an operation, what happens, what authority it requires and what a retry or failure means. Replace issue-history introductions and jargon with a concrete reason the next engineer needs. Keep durable decision links in the owning README where useful. Add length when it clarifies a subtle behavior.
5. **Set the tone with Account.** Trace account deletion from the app through the API to the worker and back to the device. Check the contract and source before using wording such as: “Starting deletion signs the person out on every device. This device keeps a receipt so it can check progress or ask for a retry after sign-out. Those two requests use the receipt and have their own rate limit.” Show where that authority comes from. Carry this clarity into the other modules.
6. **Make READMEs useful on a first visit.** Walk a newcomer through a real user or operator journey. Explain the module's ownership, public entry points, dependencies, important side effects, and how to run its focused checks. Include a small Mermaid diagram where relationships or timing are hard to see and a concrete, sanitized example where it explains an API, command, state or failure. Preserve operational recovery instructions, table/job ownership, erasure and lock rules where they apply. Verify links, commands and examples. Distinguish implemented behavior from what someone actually verified on a running system. Keep archive material as history and immutable design/vendor inputs intact.
7. **Validate incrementally and together.** Run focused tests per commit and the required full checks on the combined head, including format, lint, typecheck, Knip, dependency boundaries, unit/integration and relevant runtime checks. Use disposable accounts/databases for destructive tests. Preserve product and privacy semantics. Record unrelated behavior defects separately.
8. **Deliver one combined PR.** Give reviewers a reading order, the areas reviewed, evidence for removals, representative comment/README improvements, verification results and unresolved candidates. Keep the checklist and next action current across compaction. Finish the repository-wide review, get one fresh review of the complete diff, and follow the dev merge/deployment workflow.
