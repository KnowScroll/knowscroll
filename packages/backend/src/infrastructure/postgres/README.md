# infrastructure/postgres

Owns: the `migrator` schema (`kysely_migration`, `kysely_migration_lock`, `migration_checksum`) and the
personal-scope lock protocol on `identity.universes` (status, privacy epoch, revision).

| Operation | Purpose |
|---|---|
| `createDatabase(settings, options)` | One process's pool and Kysely instance. Sets `application_name`, `statement_timeout` and `idle_in_transaction_session_timeout` on every connection. `close()` ends the pool once. |
| `migrateToLatest(db, registry)` | Applies pending migrations from the static registry (`migrations/`) inside Kysely's migration lock, as **one** transaction: a failure rolls back the whole batch (`failed`, nothing applied), so no migration may use non-transactional statements such as `CREATE INDEX CONCURRENTLY`. Forward-only. Refuses text that does not match its recorded SHA-256, an applied migration whose recorded checksum (`migrator.migration_checksum`) differs from the registry, and an applied migration missing from the registry. |
| `readLatestMigration(db)` | Newest applied migration name, or `none`. Used by `GET /health`. |
| `makeWithPersonalScope(db, { lockTimeoutMs })` | The only way to obtain a `PersonalScopeTx` (blueprint §19). BEGIN → `SET LOCAL lock_timeout` → `SELECT … FROM identity.universes WHERE id = $1 FOR NO KEY UPDATE` → recheck existence, status, privacy epoch and (account actor) owner and account status **after** waiting → run the work → commit. Refusals are typed (`universe_missing`, `universe_suspended`, `account_mismatch`, `epoch_changed`) and write nothing; a lock wait beyond the timeout throws `ScopeBusyError` (retryable, 503). |
| `makeWithResolvedPersonalScope(db, { lockTimeoutMs })` | Identity's `WithResolvedPersonalScope` (sign-in, S1.3): one marked transaction in which `resolve(tx)` first takes identity's earlier locks (address, then sign-in link) and may create the account and its universe root, then the root is locked and rechecked exactly as above, then `work(scope)` runs. A stop, a refusal or an exception rolls back everything `resolve` wrote. `resolutionTransactionOf(tx)` gives identity's adapters the transaction during the first phase only. |
| `transactionOf(scope)` | The transaction behind an open scope, for adapters only. Throws `ScopeClosedError` once the transaction ended. The scope's `authority` is a frozen copy. |
| `enterSharedRoot(scope, rootLock)` | Locks at most one shared root after the personal root, in the same transaction, and returns the `SharedScopeTx` shared-scope ports need; a second call throws `LockOrderError`. |
| `withTransaction(db, purpose, work)` | A short marked transaction without a personal lock, for bookkeeping that must not depend on current authority (the attempt ledger's settlement). ESLint rejects the direct forms of Kysely's `transaction`, `startTransaction` and `connection` elsewhere in apps and backend code (`pnpm lint:probe` proves it in CI); aliasing beyond that is left to the runtime guard and review. |
| `makeAuthorityHolds(db)` | Identity's `AuthorityHolds` port: the same checks as `withPersonalScope`, read without a lock and without writing. For decisions that change nothing (the reasoning engine's output eligibility); whatever applies the result rechecks under the lock. |
| `advanceScopeRevision(scope)` | `revision = revision + 1` on the locked universe; the value sent in `scope_changed`. |
| `assertOutsideTransaction(adapter)` | Network adapters (model, provider, media) call this first; inside a guarded transaction it throws `NetworkInTransactionError`. Guarded transactions also refuse nesting (`NestedTransactionError`). The marker is an `AsyncLocalStorage` flag: it carries no transaction. |

`database.generated.ts` is generated by kysely-codegen from the migrated schema
(`pnpm --filter @knowscroll/backend db:types` with `DATABASE_URL` set). CI regenerates it in the
`build` job with `--verify` and fails if the committed file is stale. Never edit it by hand.

Lock order (blueprint §19): personal root first, then that universe's rows, then at most one
shared root. Never lock another person's root inside a personal scope. Identity's sign-in takes
its own two locks before the root (address, then sign-in link; `modules/identity/README.md`).

Conventions (blueprint §5): one PostgreSQL schema per backend module; explicit names (no
camel-case plugin); personal rows keyed `(universe_id, id)` and referencing the personal root with
`ON DELETE RESTRICT`; bounded JSONB with a version; counters (revisions, epochs) are 32-bit
integers, IDs are UUIDs (UUIDv7 when minted by the server, `infrastructure/ids`).

The nonpersonal reasoning root protocol is `makeWithProductionScope(db, { enabled, lockTimeoutMs })`:
`reasoning.production_scopes` root lock → enabled/generation recheck → runtime-expiring
`ProductionScopeTx`. `productionTransactionOf(scope)` gives adapters its existing transaction;
`makeProductionAuthorityHolds` checks output eligibility without a lock. These types live on the
reasoning framework-free public surface. The dependency rule permits only this protocol file to
import those **types**, and still forbids runtime imports. It never acquires a personal root and
uses `withTransaction`, so nested entry and network guards remain active. See reasoning/README.

Account-fence extension (#246): both personal-scope builders explicitly use READ COMMITTED.
Identity takes sorted account-row SHARE fences before a pair's single shared root, or its own
account UPDATE fence before an access mutation. `claimAccountFence(scope, 'pair' | 'own')` reserves
one such gate before SQL and rejects second gates or acquisition after shared-root entry. It does
not lock an account itself; Identity owns that SQL. A separate authority SELECT after all account
locks sees an epoch changed by a preceding lifecycle transaction even if that transaction only
locked, without updating, the account row. A joined locking SELECT or an old REPEATABLE READ
snapshot cannot provide that guarantee. Existing personal root, transaction timeout, network,
shared-root and capability lifetime protections remain in force. No peer personal root is locked.

`makeWithCutroomReceiveScope` (#373) owns a separate live WeakMap for the Content receiving root.
It locks only `content.cutroom_receiving_state`, re-reads enabled/generation after waiting, and
expires the capability in `finally`. No root is seeded; process configuration and actual root
admission must both be enabled. Historical recovery can read receipts under a disabled root,
but cannot admit an asset. Paid/accounting/preparation/personal/copied/closed objects fail its
getter. The generic type parameter avoids an infrastructure-to-module dependency; it does not
replace the runtime live-map check. Transactions retain nested-transaction and external-I/O guards.
