# Core ownership

Pure deterministic selection and validation live here. No database, HTTP, provider, or UI imports. As of ADR-0028/#114 the Composer is `composer-signals-v2`: a versioned, immutable policy scores and diversity-ranks a signal snapshot (exposure count/recency, unread, source — nothing else) fetched by the caller (`packages/db/src/composer-signals.ts`) and renders one registered explanation per candidate; the caller persists that same output as `decision_signal` rows so a later reader can recompute and check it rather than trust it. Do not describe this as the target design's full multi-term utility engine — it is a deliberately smaller, SQL-primitive ranking (ADR-0028). Add cognitive utility, provenance and uncertainty through a further Composer issue and target design when one exists. Changing ranking requires a new policy version and journey evidence, never a code-constant edit to the scoring function. `composer-signals-v1` (migration 0019) predates the coverage tie-break added by `composer-signals-v2` (migration 0021, ADR-0029 amendment, #113): among candidates the score cannot separate, v2 prefers the source with fewer recorded exposures in this universe before falling back to v1's hash-of-`assetId` tie-break, so no source can sit behind another indefinitely. v1's row remains registered and immutable but is never loaded by any code path from here on.

`src/semantic/bridge-validator.ts` (ADR-0031) is the pure bridge validator: a closed rejection vocabulary, versioned as `bridge-validator-v1`. A rule change is a new validator version, never an edit that silently changes past decisions; `sliceReadSet` must keep re-deriving recorded decisions exactly.
